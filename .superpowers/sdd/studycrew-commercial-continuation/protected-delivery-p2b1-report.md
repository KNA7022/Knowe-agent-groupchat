## Implemented protocol

- `ProtectedEvents` is an explicit backend adapter with a typed `ProtectedEventCommit(reference, created)` receipt. A receipt means the encrypted SQLite event transaction committed; it means neither recipient receipt nor notification intent nor task finalization. No arbitrary event dictionary/model flag can grant access. The private emit accepts a real selected P1 access object and DELIVERY outbox ID, independently resolves its committed completion, and derives the message.
- Existing verified MasterKey encrypts a bounded closed message. Domain-separated keyed AAD binds runtime key/store identity, selected physical completion store, project/group/task/completion/outbox, immutable event ID, seq, event type and keyed semantic digest. Existing P1 opaque-ID rules are unchanged; event IDs have their own private `p2evt_` domain. Header MACs are checked before refs are returned; body canonicalization/semantic MAC and lineage are checked on final hydration.
- `studycrew_protected_events_v1` and `studycrew_protected_event_heads_v1` in the selected existing completion DB commit event, identity and high watermark in one transaction. Dedicated event and runtime-catalog connections explicitly set SQLite `synchronous=FULL` and `secure_delete=ON`; this does not change all legacy SQLite connections. Same selected task/outbox retry returns the authenticated original ref/seq/ciphertext, including after actual outbox acknowledgement. Caller-supplied content is not accepted, so semantic conflict is not resolved by overwriting an event. Event timestamps are from the committed completion, excluded from the semantic digest.
- Hub holds its sequence gate through authority commit and ordered **reference** enqueue, never a network wait. Failed commit yields no receipt/seq/live output. Commit→enqueue failure propagates and requests resync; retry does not append the older sequence behind later events. Both zero and nonzero replay cursors consult Store's authority merge when protected authority is bound; the late self-review regression specifically covers a committed tail absent from the ring.
- JSONL, gzip, ring, idempotency cache, snapshot conversation and live/ordered Client queues carry refs only. Store discards derived protected copies and merges authenticated authority refs, rejecting a legacy/protected seq collision. JSONL append failure or missing gzip does not remove the committed output. Public transient hydration uses the original `message` contract: useful answer/wait/failure text, completion evidence in existing `metadata`, stable identity/status/ts/seq; private reasoning is never projected.
- Actual successful WS token upgrade installs hydration on the accepted connection. Actual HTTP `_health_conn` token admission installs a per-connection writer capability. Both share a canonical group/project and current-lineage projection immediately before serialization/send. Client hydrates **after** acquiring its send lock; lifecycle locks do not span socket await. Invalidation winning before hydration prevents output; bytes already handed to a socket cannot be recalled.
- Automatic WS replay, HTTP `/api/events`, and HTTP `/history` are current-scope strict. Only explicit authenticated `protected_history` dispatch uses P2a completed-history after configuration change. `/api/events` returns actual message DTOs, not refs masquerading as `InboundEvent`, and scope failure returns content-free 409 without a successful cursor. `/history` keeps its existing reduced history-item shape (answer content and display metadata, not full evidence DTO); full evidence remains available through message delivery/delta/explicit WS history. No HTTP read performs claim/ACK/finalization.
- Private revoke is durable before child event cleanup. Existing TaskRuntime group deletion paths discover/purge this authority before their normal cleanup. Task-scoped cache invalidation and read guards fence pending sends. Content-free authenticated highwater is retained in the runtime DB before the last encrypted path catalog entry is removed, so purge/reopen cannot reuse seq. Interrupted cleanup is retried on supported startup/deletion lifecycle paths.

## Narrow child-store discovery

P1 stores keyed child-path identities but cannot recover a concrete path on process reopen. The approved narrow catalog `studycrew_protected_event_stores_v1` reuses the verified runtime DB/MasterKey. Its only clear selection field is project ID; username-bearing path, group/task/store descriptor are encrypted. Registration uses the concrete backend-selected existing completion store after a selected P1 read. Recovery authenticates the descriptor and original lineage, verifies the keyed exact path identity, refuses missing/changed resolved paths and symlink/junction components, and never uses a model/event-supplied path or relocation fallback.

Catalog registration precedes event commit, in a separate database transaction. A failure between them may leave harmless encrypted discovery metadata, not a falsely committed event or authority. Purge and runtime watermark/path retirement are also cross-store steps, protected by the earlier durable revoke and idempotent retry. **No cross-store atomicity claim.** No unknown paths are backfilled. Corrupt metadata/missing key/path fail closed rather than plaintext recovery; manual repair/key recovery is outside this slice. The catalog is not a general storage registry. Removing the final event removes its private path metadata after verified cleanup; retained heads/opaque revoked receipts contain no message body.

## Self-review and limitations

- Python skill guided explicit async queue/send-lock boundaries, custom authority errors and real async/SQLite fixtures. New module has one purpose, completion-derived protected delivery; existing Hub/server are large files and were changed only at necessary admission/public-output/replay hooks. No broad legacy persistence rewrite.
- The semantic event authority is durable independently of caches. Future P2b2 must await this receipt **and** all required notification intents before outbox ACK/task finalization; this slice intentionally does not wire those effects or claim original Unit P complete.
- Tests exercise transaction faults and real SQLite close/reopen, not abrupt OS process kill or hardware power loss. SQLite FULL configuration is not hardware/storage-stack power-loss certification. Existing MasterKey backup/rotation, remote copies, old encrypted WAL pages and hostile same-user memory inspection are not solved here.
- Authority still uses synchronous bounded SQLite operations inside the Hub sequence gate/current guard. Correctness is verified, not production throughput under slow disks or many clients. No performance certification or multi-process multi-writer stream claim.
- Missing key/corrupt catalog require explicit recovery; no relocation or silent plaintext fallback. Reparse/path guards are implemented, but a hostile concurrent OS path-swap race was not simulated. No blanket crash-atomic guarantee across runtime DB and child DB.
- Automatic replay/current scope and explicit completed history remain distinct. Public plaintext is transient and cannot be recalled after socket handoff. Existing `/history` UI intentionally shows its legacy compact item format; no frontend changes or rendered browser test was needed/performed.
- Existing Controller documents and `skills/` are excluded from the implementation commit. New dependencies: none. External provider calls: none.

### Changes

- **I1:** A fenced Client now admits its prescribed `state_snapshot` into the existing ordered queue. The stream-sequenced, specific queued snapshot object is the pending recovery identity. Live events committed after its capture are retained behind it rather than dropped. Only that snapshot's real final `Client.send` success clears the fence; initial replay buffering is not success. A failed hydration/send clears pending recovery and same-project successors but retains the fence. The already-issued resync notice is preserved, without recursively producing a new automatic snapshot retry loop while authorization remains unavailable.
- New resync invalidates the pending snapshot identity even if that earlier handoff is already awaiting the socket. Scoped revoke invalidation examines the pending **reference-only** snapshot and invalidates it as well. When an older await finishes, identity mismatch prevents clearing a newer fence. Tests explicitly interleave a second snapshot and later live event behind both new resync and real revoke. Bytes already handed to the socket remain non-recallable, as before.
- **I2:** Actual `KnoweServer._do_replay` checks each required `Hub.send_to` result. Failure requests resync and returns immediately: no later event, no `replay_complete`, no cursor advancing past an unsent record, and no following unread-count work that could mask a missing-key failure. Generic `Hub.send_to(replay_complete)` no longer releases protected recovery state. Current-scope snapshot handoff is the fence-release path for the established protocol; no frontend/new API change.
- Initial live-replay-buffer release respects the project fence and turns an admitted protected send failure into resync instead of discarding the gap silently. Unrelated project buffers are not discarded on that protected failure. All pending recovery state remains opaque refs, never hydrated message bodies.

## Fix round 2 — I3 visible retry after recovery overflow

FIX_BASE: `4247eea45a7ffca0840aea153e5537a38ef904af`. Controlling review: `reviews/REREVIEW-protected-delivery-p2b1-fix1-4247eea.md`. Independent review marked I1/I2 addressed; this round only fixes I3 in the pending-recovery queue. Re-review of this fix remains required, and P2b2 is not started.

### Narrow protocol correction

`request_resync` captures the exact pending snapshot it invalidates. When a new invalidation removes that identity (including queue overflow while its socket await is in flight), it queues one fresh `resync_required` after the stale handoff, unless a same-project notice is already queued. Popping the pending identity ensures repeated invalidations do not multiply notices; queue scanning coalesces an already-pending notice. Same-project successors remain fenced until a current snapshot succeeds. The notice contains no decrypted message content and uses the existing frontend request-snapshot protocol.

A recovery snapshot's own failed final handoff passes `failed_handoff=True`, retaining the fence without emitting a notice that would recursively trigger more denied snapshots. This flag is only applied **after** the existing exact pending-identity recheck: if a newer overflow/resync already invalidated the old handoff, the old await returns through the identity-mismatch branch and cannot suppress the newer notice or recovery identity. This is not a permanent per-client suppression flag. No new timers, generic recovery framework, public API, frontend changes, storage/crypto changes or I1/I2 redesign.
