## Revoke, purge and retirement

- Persist the existing revocation/deletion fence before child cleanup. Late selected writes and readers fail under the existing P1/P2a rules. After revocation, use a narrow authenticated cleanup path for only originally owned artifacts; do not briefly restore RUNNING, issue live capability, or relax guard(write=True).
- Invoke actual P1 completion/journal/outbox/receipt and TaskEnvelope cleanup for the selected task and accepted P2b1 event cleanup/cache invalidation. Preserve unrelated lineages in the same physical DB, other Groups and legacy rows. Close only owned views/handles as needed; a shared store or legacy connection is not permission to delete the whole file/directory.
- Missing/uncreated artifacts after enrolled-but-interrupted setup can be treated as already absent only after authenticating their expected identity/location. Corrupt selected metadata, changed paths, key failure and cleanup I/O errors must leave a visible retryable failure or explicit recovery requirement; never falsely report purged or silently fall back to unknown files.
- Keep discovery metadata until ALL owned child artifact classes are confirmed cleaned, not merely until event rows are absent. Retry interrupted cleanup from the existing supported startup/deletion/quarantine lifecycle. Unrevoked enrolled work on startup must not be executed, repaired, claimed, ACKed or finalized. Preserve accepted content-free stream high watermark and deletion/revocation receipt; retire private path metadata only after safe completion.

- Runtime quarantine caused by invalid Group deletion proof is a fence, not valid deletion authority. Unrevoked quarantined records must remain retained and unreadable/unwritable for execution; only an independently durable existing revoke or valid deletion proof permits cleanup/retry. Test these two cases separately rather than purging user data on an invalid proof.
