## Required foundation

1. Add a validated private bound-card state contract and a backward-compatible nullable encrypted representation on the existing approval rows. The actual approval relation supplies canonical group/run and its task identity; model/renderer card fields cannot establish ownership. Null legacy state stays unbound, with no migration from history or latest group run. State has bounded instruction/display fields, target role, content generation, state version, feedback epoch, source/course revision and typed lifecycle receipts. Reserve identity/policy/version fields against input overwrite. Keep sensitive data out of ApprovalRequest.to_dict, public runtime snapshots/events and generic logging.
2. Inject the verified existing MasterKey capability into the card repository boundary; do not add a new key-file format, dependency, environment fallback or renderer key. The later composition-root integration will reuse the established DPAPI key. Generic old runtime operations may operate without this optional capability, but every bound-card read/write must fail closed without the right key. Use AES-256-GCM, fresh nonce per write, strict canonical UTF-8 serialization, domain-separated AAD binding stable store identity/key/group/task/run/approval/generation/epoch/state version/field. Use keyed equality digests for sensitive proposal text. Authenticate clear versions. Verify a persistent key sentinel before accessing existing encrypted rows; wrong/missing/corrupt keys or envelopes must not overwrite or regenerate existing data.
3. Provide narrow transactional service/store operations to create a pending bound card from a real canonical ROUTING/RUNNING owner, read an authorized current snapshot, perform a versioned amendment and resolve the current proposal. Creation stores state, approval and WAITING_APPROVAL transition atomically before any projection. Existing active group/deletion, task identity, single-pending-approval and finite expiry rules remain binding. Creation never publishes raw card content or starts a worker/provider/tool.
4. Amendment and approval compare the same generation and keyed proposal digest in the same row/transaction boundary. Amendment requires the actual pending approval and owner still WAITING_APPROVAL; increments content generation and state version, replaces the digest, and cannot carry an approved grant. Approving stale/missing versions, cross-group cards or nonpending/expired/terminal owners grants nothing. Reject/cancel may invalidate a pending card but cannot dispatch. Generic approval resolution must not approve this purpose without the new exact version checks. Concurrent amendment versus approval has one valid winner, not an old-version approval of new text. Duplicates are bounded and idempotent; request-key reuse with conflicting payload is rejected.
5. Revocation, expiry and terminal-state checks must apply to reads and mutations, not only UI. Deleted/archived/quarantined group or removed source/course revision fails closed. Store only opaque metadata/receipts when invalidated; preserve established deletion hygiene. This slice may use an explicitly injected, backend-owned scope validator to bridge existing group/source checks, but cannot accept a caller-supplied boolean or renderer scope as authority. Do not hold a transaction across any await or external call.
6. No provider or feedback child is created in this slice. Do not expose a new renderer endpoint or alter legacy allowlists. Do not implement the full encrypted Hub history/TaskEnvelope adapter yet, and do not send these new private snapshots through their existing plaintext serializers. Existing legacy cards remain unsupported by this foundation. Name the exact subsequent integration seams in the report.
