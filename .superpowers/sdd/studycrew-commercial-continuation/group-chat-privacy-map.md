## Finding

New StudyCrew Groups still use the legacy project adapter for ordinary user/coordinator chat. This is newly generated Group content, not merely old files remaining on disk. Protecting a later Worker completion does not retroactively protect the original prompt, routing continuation or ordinary coordinator final. The actual pre-proposal ingress needs a Group-scoped encrypted storage boundary before Unit D can claim end-to-end private handling.

The trace proves plaintext event and runtime-request writers and an ordinary coordinator memory projection. It does **not** prove a disk dump of the coordinator's full raw tool history, nor that ordinary user/coordinator messages enter SeenSpeech or report files. No public-internet exposure or unauthorized provider call is claimed. The reasoning issue here is inclusion of raw model reasoning in the ordinary client-visible event lane, even after text sanitization.

## SeenSpeech and reports: limits of this finding

`backend/engine.py:2924` records SeenSpeech only inside `_emit_completion_visible` (`:2904`), using a completion view. `backend/seen_speech.py:100`/`:112` is indeed a plaintext ledger writer, but this selected ordinary coordinator final route does not call it. `backend/engine.py:4512` invokes `handoff.write_report` from Worker handoff reporting; `:9343` is a deprecated forwarding API. Neither is established as a new ordinary user/coordinator chat sink here. Their protected Worker dispositions are already in `protected-lineage-discovery.md:93`–`:100` and controller decisions `:115`–`:116`; retain those planned skip/encrypted-notification behaviors without reopening P2b1.

Model output can echo tool/private content into a final or proposal. That justifies protecting the proven final/proposal storage boundaries; it does not justify asserting that every possible raw tool result was written to every legacy sink.

## Smallest upcoming integration prerequisite

1. **Admit local private Group content before echo/routing.** In the existing authenticated command boundary, resolve the canonical Group and current lifecycle under the existing Group fence. Accept a bounded text request into encrypted local storage through the existing repository/event boundaries, using a backend message identity and Group identity. Retain ciphertext or an opaque authenticated reference before the first Hub ring/JSONL write. The input record must not require a nonexistent TaskRun or fabricated bound card. A transport client ID may identify the current session, but must not become a durable decryption identity that breaks after restart.
2. **Bind real execution later.** Route the transient decrypted input normally. Once the actual TaskRun exists, persist an exact backend-owned message→Group/task/run association. The generic runtime event and continuation rows must carry only bounded metadata plus encrypted content/reference, including approval-wait and recovery paths. No input-content regex may decide whether new Group data gets encryption. Model/renderer run fields cannot provide this authority.
3. **Keep coordinator-derived content on the same protection policy.** New proposal/tool-result history, final/error messages and historical generations must retain their immutable message/turn ownership through the existing producer, card and continuation paths. Keep raw provider messages transient; if restart requires a tool-call/result transcript, use an explicit encrypted history representation at the existing storage boundary. Do not assume the current in-memory `_history` already supplies restart persistence. Reusable raw history needs scoped authorized hydration, not retention in public/replay caches. Public projections exclude raw reasoning entirely; encrypting reasoning while still publishing it does not satisfy that requirement.
4. **Close the reached optional copy.** For this initial source-free Unit D route, prevent `_schedule_project_memory` from copying new private turns into plaintext JSONL/context snapshots; use an explicit content-free skip until an encrypted memory adapter is in scope, or seal only that reached adapter. Preserve useful encrypted chat/card history. Do not silently invoke legacy report/knowledge side effects when dispatching.
5. **Reuse accepted Worker lineage after approval.** Unit D still owns real coordinator ToolRegistry → metered proposal → displayed-version approval → scheduled exact dispatch → protected Worker. Input admission is storage authority, never provider/tool permission. Keep RUNNING-only provider authority, exact grants and canonical Worker composition intact. On restart, authorized history hydration must not itself queue coordinator or Worker execution.

This can be implemented by a narrow Group-content mode in the existing persistence/composition boundaries and opaque references in existing runtime rows. It is a design recommendation, not a claim that a pre-run Group codec/API already exists. Do not broaden `ProtectedAccess` by supplying fake task/card identities: `backend/protected_storage.py:259` and `:269`–`:283` require actual lineage, owner and current card.

Verified reusable building blocks:

- Local key lifecycle: `backend/local_knowledge.py:43`–`:46` uses the existing DPAPI-protected `master-key.dpapi`; `backend/knowe_rag/crypto.py:181`/`:186` provide seal/open. `backend/knowe_rag/store.py:179` verifies the key. Composition must inject this verified capability explicitly, not access renderer credentials or introduce another key file.
- Runtime key sentinel/envelope: `backend/task_runtime/card_state.py:168`–`:191` fail closed on absent/wrong sentinel/key; `backend/task_runtime/service.py:132`–`:137` accept an injected card key. `backend/protected_storage.py:94`–`:106` verifies that same capability. Reuse crypto/domain separation and record-AAD principles; existing Worker lineage authority is not pre-run authority.
- Group/session: `backend/groups.py:414` supplies the in-process admission guard, `:490`/`:496` canonical lookup/resolution; the WebSocket authentication and Group/project cross-check above supply the current local user session. Existing deletion fences at `backend/server.py:925`–`:927` must remain checked. No new accounts, permissions model or scheduler is required. The guard is explicitly not a cross-process lock.

## Placement and existing plan coverage

The design already requires encrypted card/dispatch copies, typed continuations and no raw-handler bypass (`card-authority-design.md:61`, `:202`, `:222`, `:265`). It explicitly left actual coordinator tool-result sinks for trace (`:267`). The current map closes that bounded uncertainty: full raw tool history is confirmed in memory, whereas pre-run echo and routing SQL content are separate concrete writers. Earlier discovery covered Worker/Hub/report/SeenSpeech projections; it did not establish pre-run Group admission protection.

The new private chat ingress, routing-request storage and coordinator projection integration are **Unit D prerequisites** for the actual real-user producer path, and therefore also a **whole-product release gap** until implemented and verified. They are not a new acceptance requirement imposed on current P2b1 event delivery, nor a reason to revise accepted P1/P2a results. Dynamic marker/reopen verification belongs to the later scoped implementation, using the real command/coordinator path and inert lowest transport.

Migration of all old project history, platform/DM chat, unrelated optional features, or all pre-existing user files is outside this finding. New protected Group records need explicit backend-owned policy that cannot silently downgrade to legacy when a marker/key is missing. Existing legacy history remains distinguishable; this report neither authorizes nor requires rewriting it.
