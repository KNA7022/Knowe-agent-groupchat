Two implementation gaps need explicit focused verification before release closure:

1. **Feedback control-plane aux authority:** `_cmd_feedback_instruction` (`server.py:5462–5496`) calls `adjust_instruction` directly; neither it nor `_run_feedback_flight` installs a card-owned Task Runtime authority. `ProviderGatewayClient` defaults to `current_legacy_tool_authority` and denies without it (`commercial_gateway.py:2439,2562`). Unlike governed turn/DM paths (`engine.py:4303,5000`), a normal WebSocket control command appears to have no authority context to inherit, so a valid aux lease alone may still leave the UI adjustment unavailable. This is a source-supported production availability risk, **not runtime-reproduced here**. Test the actual command with an inert gateway transport and an authoritative card/run. If confirmed, derive authority only from the durable pending card and its owning run, validate lifecycle, and carry it into the cancellable flight. Never accept renderer/model supplied IDs as authority or fabricate a broad background run.
2. **Configured zh Worker language:** `worker_gateway_runtime.py:342–348` asks `resolve_prompt_path`; `prompt_resolver.py` returns `None` when the language-specific file is absent, and both language-specific Worker files are absent. If zh is contradicted, make the canonical rule refer to the actual configured active language (or its governed prompt context), preserving one canonical Worker protocol and no natural-language inference/translation. Do not merely remove the two failing language assertions.

The Zinnia platform gap and unmigrated external tool denial are explicit security migration limitations already visible in source. Updating legacy success assertions must not claim those features are restored.
