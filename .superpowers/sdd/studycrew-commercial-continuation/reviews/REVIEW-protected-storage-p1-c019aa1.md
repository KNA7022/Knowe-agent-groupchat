## Important

1. **Clear query values can persist private text.** `backend/protected_storage.py:389` validates timestamps and selected opaque IDs but leaves `route_key` and numeric/state fields unchecked. `backend/knowe_harness/completion.py:1396` then inserts the derived route in clear, and `backend/knowe_storage/task_run_repository.py:87` directly inserts the supplied version. Two focused real-repository probes confirmed this: (a) replace a stored CompletionEvent's delivery intent with `{'audience': 'user', 'channel': MARKER}`, then call public `transition_completion(..., CANCELLED, ...)`; the new outbox route contains MARKER; (b) assign MARKER to an actual TaskRun's version, then call protected `SQLiteTaskRunRepository.create`; SQLite's INTEGER-affinity column stores the marker string verbatim. Both operations succeed. This violates the explicit clear-field schema and no-plaintext durable-index requirements. Validate every clear column with strict types/allowed enums and bounded opaque identities, and bind delivery routing to the canonical permitted target before mutation. Add behavioral tests asserting denial and absence from DB/WAL.

2. **Protected collision errors disclose provenance content.** `backend/knowe_harness/completion.py:1767` propagates `str(exc)` from provenance comparison as `CompletionConflict`; the same pattern occurs at `:1534`, `:1806`, and in `backend/knowe_storage/task_run_repository.py:72` / `:119`. The unchanged comparator (`backend/knowe_provenance/model.py:173`) includes arbitrary accepted `provenance_id` strings. A focused probe committed a protected run with valid recorded provenance whose ID was MARKER, then recommitted the same run with a different provenance ID. The resulting CompletionConflict message contained MARKER. Encryption of the stored provenance does not prevent this diagnostic leak. On protected paths, translate these collisions to a fixed content-free error with suppressed sensitive chaining; preserve detailed legacy behavior if needed. Test exception text and formatted traceback for create/save/completion/delivery collision paths.

3. **Acknowledgement retry accepts an unauthenticated retained receipt.** `backend/knowe_harness/completion.py:2654` uses INSERT OR IGNORE for the receipt and then deletes the outbox at `:2674`; it never opens an existing receipt before reporting success. A focused probe acknowledged an outbox, corrupted its retained receipt payload to `{}`, recommitted the same completion to recreate its outbox, and acknowledged again. Acknowledgement succeeded and removed the outbox; `projection_receipt` still failed authentication afterward. Checking that the identity claim exists in `backend/protected_storage.py:303` does not authenticate the existing child ciphertext. Authenticate the collision row, independently check its identities and keyed equality, and fail without deleting the outbox on corruption. Apply the same requirement to the other newly adapted INSERT OR IGNORE retry boundaries (`completion.py:1204`, `:1396`, `:3048`) rather than silently accepting their existing payloads.
