## New Breakage in the Fix Diff

- **Important I3 — Queue overflow during a recovery handoff leaves an invisible permanent fence.** At `backend/hub.py:167`, queue overflow calls `request_resync`. The new implementation at `:202` removes the pending recovery identity and same-project queued successors even when the project was already fenced, but `:209` emits a notice only when it was not already fenced. If the recovery snapshot is already awaiting `ws.send`, that snapshot can subsequently succeed. The new identity check at `:192` correctly prevents the stale handoff from clearing the newer fence, but no replacement recovery notice or snapshot is queued. The client receives an apparently successful snapshot, while the server has no pending recovery and silently discards all later project events. Existing tests explicitly request a second snapshot after their injected new fence (`backend/tests/test_protected_events.py:739`); they do not cover this automatically triggered overflow where the client has no knowledge that another request is needed.
- **I3 trigger and consequence:** initial committed-enqueue failure → `resync_required` → actual `request_snapshot` → snapshot held inside socket send → enough later live events fill the ordered queue → one further event triggers overflow → release the old snapshot. The old snapshot reaches the client but covers only the state captured before the overflow. The lost successors remain durable; they are not delivered automatically because the project remains fenced without a fresh notice. This reproduces on a healthy authenticated socket without scope/key denial or storage failure.
- **I3 required correction:** preserve a bounded, ordered recovery signal for a newly invalidated in-flight recovery generation. A stale successful snapshot must be followed by a new recoverable notice or a safe replacement snapshot; later events must remain fenced until a current snapshot is successfully handed off. Distinguish this new invalidation from repeated hydration denial so the fix does not create an authorization-failure retry loop. Add an actual request-snapshot/overflow regression which does not manually supply the missing second request before observing a new signal.
