# Pending Agent card authority — bounded integration design

Design only, 2026-10-04. Inspected working-tree source with HEAD `7199835`; the concurrent baseline implementer's files were not edited. Read the design brief and backend regression triage. Applied Backend Python Expert and its complete asynchronous-pattern reference: lifecycle-owned tasks, bounded waits, cancellation propagation, and durable checks around asynchronous boundaries. No provider/network calls, tests, production changes, index changes, or branch changes were performed. This report is not authorization to start implementation before the baseline gate.

## Decision

Make a new `propose_next` card a projection of an existing Task Runtime approval owned by the actual governed coordinator run. Persist that relationship and the authoritative card content before publishing the card. A user's feedback request may create one narrowly scoped foreground SIDE run, linked to that owner and exact card generation. Only the scheduled, RUNNING child obtains provider authority. The parent remains WAITING_APPROVAL. Keep Provider Gateway's RUNNING-only rule unchanged.

An unowned legacy card cannot acquire authority through feedback, approval, event replay, a supplied run ID, or association with the latest run in its group. Display it as historical/expired and offer a new governed proposal. Do not create a background owner to make a denial disappear.

## Durable representation and admission

Use the existing `studycrew_approvals` row as the card identity. For new bound cards, use the runtime approval ID as `card_id == card.approval_id`; verify opaque-ID handling across the renderer rather than introducing an `ap_`↔`apr_` identity registry. The runtime approval contains the owner run/group; task identity is checked against that run.

Add nullable encrypted `card_state_ciphertext BLOB`, `card_crypto_version`, `card_key_id` and `card_state_version` fields to that table, with a validated decrypted schema and narrow repository methods. Do not introduce plaintext `card_state_json`. The private operational snapshot contains the card kind/target/body, owner task identity, content generation, feedback epoch, latest request/child binding, bounded receipt and source/course-scope revision. Its ciphertext is excluded from `ApprovalRequest.to_dict`, runtime public snapshots, audit events and generic payload dumps. Only the authorized rendering or card-operation boundary decrypts the bounded data needed for that operation. A null ciphertext explicitly means “not a bound card”; migration must not fill it from conversation text.

### Encryption and every derived copy

Reuse `MasterKey.seal/open` and the existing application's DPAPI-protected key lifecycle, injecting the verified key capability into the runtime repository from the composition root. Do not read credentials or key bytes from renderer fields, environment variables or provider leases. The currently verified production seam is `LocalKnowledgeService` → `MasterKey.load_or_create(data_root/master-key.dpapi)`; `MemoryRepository` accepts an injected MasterKey and demonstrates the same encrypted repository pattern. Do not falsely describe a master-key lease as already integrated here: SecretLeaseBroker supports that kind, but these repositories currently use the DPAPI seam. No new key-file format or parallel secret registry is needed.

The new field envelope is version 1, fixed algorithm AES-256-GCM, opaque key identifier/version, state version and `nonce || ciphertext || tag` from `MasterKey.seal`. Encode the private object as strict UTF-8 canonical JSON before encryption. Construct AAD with `field_aad(canonical_json(["studycrew.card-state", 1, store_instance_id, key_id, group_id, owner_task_id, owner_run_id, approval_id, content_generation, feedback_epoch, card_state_version]), "studycrew_approvals.card_state")`. The store instance identifier is stable repository metadata, not the rotating runtime recovery epoch. Use a different domain/table/record-field binding for encrypted feedback requests and dispatch envelopes. Validate all clear identity/version fields and then authenticate them through AAD; copying ciphertext across rows/groups/fields or changing a generation must fail. Increment state version and use a fresh nonce on every state update, including updates that do not change the instruction generation. Compare versions and replace ciphertext in the same approval transaction. AAD prevents substitution, not rollback of an entire stolen database; do not claim rollback protection that the storage layer lacks.

Before opening existing encrypted card state, verify a domain-separated encrypted key sentinel as the encrypted repositories do. Missing/wrong/corrupt key, absent sentinel with occupied encrypted fields, unsupported envelope version or authentication failure must deny card reads/writes/egress with a typed storage error; never regenerate a key, overwrite ciphertext or fall back to plaintext. Seal before passing any content to SQLite, so the DB, WAL, temporary files and backups contain ciphertext. Reuse secure-delete/checkpoint deletion hygiene. Retain only opaque IDs, lifecycle values, bounded numeric versions and keyed digests as clear metadata. Use domain-separated `keyed_content_hasher`/HMAC for proposal/feedback equality digests outside ciphertext, not unsalted SHA-256 fingerprints of short sensitive text. The existing exact Provider Gateway request digest remains a distinct egress-consent scope; it must not become a new content audit field.

Apply the same encrypted envelope to feedback continuation private requests: the present `private_request` JSON field is not encrypted and must hold only an opaque encrypted-payload reference or ciphertext envelope for this new kind. Card feedback must never be copied into its plaintext `payload_json`, run events' `sensitive_payload_json`, generic exception strings, tracing, or diagnostic logs. “Private” and “sensitive” labels do not provide encryption.

For new bound cards, separate the render projection from persistence: Hub's event ring/idempotency cache and `persist.Store.append_event` retain only card identity, generation, status and an encrypted snapshot/reference. Hydrate the authorized card body just in time for authenticated broadcast/replay, with fresh lifecycle checks. Do not send a hydrated event through the existing generic JSONL writer or retain it in a plaintext replay cache. Store the encrypted historical generation snapshot when history must reproduce prior content; metadata-only pointers to a mutable current row must not rewrite history. Gate caches identity/future rather than a durable plaintext body. Short-lived in-memory plaintext is necessarily used while rendering or assembling the model request; release references when that operation ends, avoid reusable plaintext caches, and do not claim that Python strings can be reliably zeroized. Check renderer disk caches as part of this card route; transient visible UI state is not permission to persist the card in localStorage or an unencrypted cache.

Approved dispatch also carries the instruction. The scoped adapter below must persist its TaskEnvelope through an encrypted serialization mode on the existing TaskEnvelopeStore/repository boundary, and queue only a transient decrypted object. Existing `.json` envelope reads and `.md` instruction/approval writes are not acceptable hidden plaintext replicas for this new path. Keep opaque references/metadata projections, decrypt through the scoped reader when execution needs the instruction, and do not invoke legacy content-writing/knowledge side jobs as incidental dispatch work. User-requested plaintext export is a separate explicit action. This is a bounded storage adapter for the new card/dispatch route, not an asserted migration of all historical Harness storage.

Approval `operation_scope` contains normalized identifiers and a digest of the exact dispatch proposal; purpose is a new exact value such as `card_dispatch`. It is not `provider_egress` or `route_message`. Ownership is the approval's actual persisted relation, not an ownership-looking field inside renderer/model card JSON. Reserve status, IDs, generations, purpose and scope fields so model-produced `card_body` cannot overwrite them.

Add a private service operation such as `request_card_approval` around the existing approval transaction. It resolves authority from the backend's governed turn, verifies canonical engine/group/task/run, active group, valid directory, correct task lifecycle, and no other pending approval. It persists the approval, private card state and WAITING_APPROVAL transition atomically. Gate publishes only after that commit and reconstructs its future from the committed row. Failure before commit emits no actionable card. Failure after commit is recovered by projecting the row; do not manufacture a new approval.

This operation must not be exposed as a general renderer “bind card to run” endpoint. If the card producer has no true governed owner, fail closed. Existing read-only legacy-tool allowlists must not be expanded to classify dispatch or platform mutations as reads.

### Required single producer → approval → dispatch adapter

The minimal deliverable includes one exact `propose_next` adapter, not just feedback on artificially seeded cards. Wire it into the coordinator's real execution boundary at `engine.bind_commercial_tool_registry`: a closed composite boundary routes the exact coordinator-only tool name/schema to a new `GovernedProposeNextAdapter`; the existing four reads continue through LegacyToolBoundary, and all other legacy effects remain denied. Do not add `propose_next` to `read_only_tools`, expose a generic raw-handler escape, or give Workers this producer route.

The adapter presents one lifecycle with two privileged phases. Its proposal phase accepts the backend-captured current governed owner and tool-call idempotency key, plus validated target/instruction/allowed display fields. It checks active canonical group/task/run, coordinator identity, roster membership, target availability, current source scope and single pending proposal. Model arguments contain proposal data only. It atomically persists the encrypted exact proposal, approval, WAITING_APPROVAL transition and opaque continuation binding, then publishes the card. Side effects in this phase are only those runtime records and authorized card display: no handoff files, TaskEnvelope commit/queue, Worker start, phase changes, memory writes or provider background work.

Its dispatch phase is callable only by the backend approval continuation, after the common generation/digest CAS has issued an exact single-use `card_dispatch` grant and the owner is scheduled RUNNING. Under the real Tool Gateway, prepare/claim an invocation whose scope binds group/task/run, approval, generation, keyed proposal digest, target Worker and one backend allocation key. Recheck source/directory/lifecycle and worker occupancy. Atomically consume the grant and establish one durable dispatch intent plus reserved target identity. Its encrypted payload fixes the TaskEnvelope task/attempt IDs before any queue effect; retries reuse those IDs, never allocate a second job. The allowed effect is precisely one persisted encrypted TaskEnvelope carrying the final approved instruction and its canonical authority, followed by one insertion into the existing Worker queue and ordinary Worker scheduling. The grant does not authorize whatever tools that Worker later requests; every subsequent provider/tool operation still passes its own Gateway checks.

Factor the necessary construction/queue calls from `commit_handoff_step`/`_create_task_envelope`/`inject_task_envelope` into this narrow adapter, preserving existing TaskEnvelope and Worker scheduling contracts. Do not call the old helper unchanged: besides queueing it performs phase changes, plaintext instruction/approval projections, asset matching, consolidation/distillation and ingestion. None is silently included in the new card's grant. Initially reject unsupported phase-changing or extra-effect fields with a clear validation receipt; retain only fields representable in the exact encrypted proposal/envelope. The adapter may emit metadata-only approval/dispatch receipts. Rejection/expiry emits a receipt and never calls the dispatch phase.

The runtime intent and Worker queue are different persistence domains. Use existing invocation/continuation claim status plus the stable TaskEnvelope task/attempt identity to reconcile a crash between them; do not promise an atomic cross-store transaction. A never-effected prepared intent may be reconciled only after all current checks and the applicable recovery policy; a claimed intent with uncertain queue effect remains blocked and is reconciled by exact envelope/queue identity without executing a second job. Reapproval cannot repeat that uncertain dispatch. This adapter, its encrypted storage/projection seam and the feedback child are one release unit. Until the real producer and exact approved dispatch tests pass, the feature remains unavailable; feedback-only success is not feature completion. No `create_project`, roster mutation, removal, shell, external-root grant or other platform migration is included.

## Feedback transaction and state rules

The wire command supplies card ID, expected content generation, an opaque bounded request ID, and bounded feedback text. Group/project fields identify the requested view; arbitrary task/run/grant fields are rejected or ignored as authority. Add these version fields to both approval-card UI and runtime-detail approval controls.

Before any child creation or egress, one service transaction validates the authenticated command's canonical group, active/non-quarantined group and deletion fence, card kind, pending approval and expiry, real owner group/task/run, expected generation, source revision, and request deduplication. A first request with a given ID records a private payload digest; a repeated matching request returns its existing queued/running/terminal receipt. Reusing an ID with different text/card/generation conflicts and does not cancel the valid request.

| Parent state | Feedback behavior |
|---|---|
| WAITING_APPROVAL, gated by this exact pending card | Admit a bounded feedback child. This is the ordinary supported state. |
| ROUTING or RUNNING | Permitted only while creating the original bound approval; publication atomically changes it to WAITING_APPROVAL. A feedback command encountering a pending card in these states fails consistency validation. |
| QUEUED or VERIFYING | Deny feedback; the proposal is no longer the active approval gate. |
| PAUSED, including recovered execution | Deny until the existing explicit recovery/resume workflow has legitimately restored a new/current waiting approval. Feedback never resumes a task. |
| SUCCEEDED, PARTIAL, FAILED, CANCELLED | Deny, invalidate pending projection, no child/provider/effect. A new user task needs its own governed proposal. |

Admit a child through a new narrow service/store transaction, reusing `studycrew_task_runs` and its unique request key. Set SIDE, FOREGROUND, read-only, LOW, parent_run_id=the actual owner, with a new child task ID and exact finite limits. Persist a private executor-continuation record with a validated `executor_kind=card_feedback`, card ID, content generation, feedback epoch, parent identity, request digest, deadline and allocation metadata. Add explicit continuation-kind dispatch; generic chat continuation execution must reject this kind. This extends the existing continuation store, not a new work registry.

The transaction increments the durable feedback epoch, replaces the active child binding, and fences the prior child. Then cancel and await the old in-memory flight. Claim the new continuation exactly once only after the normal scheduler has made its child RUNNING; waiting for capacity has a deadline and does not spin or block an event-loop thread. Never call `transition(RUNNING)` to bypass scheduler capacity.

Inside the lifecycle-owned flight, reconstruct only the child's authority, explicitly install/reset it around aux, and never rely on the WebSocket task's inherited context. Immediately before provider egress, recheck card/parent/child/epoch/group/source/deadline and child RUNNING state. Preserve the general Gateway checks; add a card-child-specific validation hook where the real Gateway authorizes this child, so an incidental reuse of child authority cannot escape its purpose. Only a single text-only chat with the frozen request digest, configured aux binding, no tools/images/history/retrieval, and bounded output is allowed.

After the await, a compare-and-set transaction rechecks those same facts plus pending approval and generation. Only its winner writes the amended instruction, feedback history, next content generation and updated dispatch digest. No successful amendment has an old grant to inherit: the parent approval must still be pending. Publish the committed snapshot afterward. Empty/unchanged/failing results publish a typed request receipt without changing content generation. Superseded responses cannot publish success or rewrite the card.

## Budgets, privileges and cancellation

Use one logical aux call, `max_retries=0`, `tool_calls=0`, explicit maximum output tokens, a payload-size limit, and a deadline no greater than configured `adjust_timeout_s`. Clamp its token/cost/wall-clock allocation to policy and remaining parent budget. Do not use the broad default 20 model turns/$5 child budget. Numerical UI tuning can be configurable within these hard caps; insufficient allowance denies before egress.

Current `submit(parent_run_id=...)` does not share budgets. Add a transactional parent allocation when the child is admitted: reserve a bounded slice on the parent without exceeding its remaining budget, persist that allocation on the child continuation, and give the child only that slice. Gateway accounts actual child use normally. Settle/refund the parent reservation once, keyed by child allocation identity; cancelled/failed calls retain conservative consumed/unknown amounts. A crash must not release an uncertain reservation or allow a repeated request to buy another slice. Reject stale parent versions and serialize concurrent allocations. Parent and child totals represent an aggregate and its component, so reporting must not double-count both. No unlimited fresh allowance on every click.

Inherit canonical group isolation, parent linkage, applicable data classification/privacy restrictions, authorized source revision, and the explicitly reserved budget only. Do not inherit grants, approved egress digests, external roots, shell/network/write capabilities, provider credentials, sensitive-data consent, or permission to continue the parent. The child being read-only describes its model/tool scope; only a separate trusted compare-and-set operation may change the proposal. It cannot dispatch a worker.

DLP stays mandatory. Card approval does not authorize transmitting sensitive content. The first release has a fixed conservative rule: sensitive-feedback Gateway denial produces a clear typed failure explaining that the content cannot be sent to the auxiliary model, with no egress. No new sensitive-egress approval UI is part of this implementation. Any future support needs its own exact child/provider/request scope and cannot reuse the card approval. Reapproval of an old dispatch cannot authorize provider egress either.

Cancellation must be durable first: card reject/approval/timeout/cancel, newer feedback, parent terminalization, explicit stop, group archive/quarantine/deletion, source revocation and shutdown all invalidate the relevant feedback epoch/child before allowing further work. Integrate this into runtime transactions, not only Gate's best-effort listener. Cancel queued children and running continuations; then cancel/await the asyncio task, close the provider client, reconcile budgets, and retain a typed terminal receipt. Preserve `CancelledError` propagation for parent shutdown. The current `TaskRuntimeService.cancel` only terminalizes the named run's state; parent-to-card-child fencing is required new work.

Validate the group deletion/source fence at admission and at egress/commit, using a shared short-lived admission critical section with the corresponding mutation seam. Never hold a database transaction across a network await. Cancellation cannot retract bytes already sent before a deletion/stop won the fence; it prevents subsequent sends and every late card mutation. Explicitly test both sides of that ordering.

## Approval, source changes and recovery

Apply one common card-resolution validator to `_resolve`, runtime HTTP/WS approval dispatch and repository service operations. UI button disabling alone is not enforcement. Require the current generation and live owning approval; approving while a feedback child is active returns a busy/conflict receipt (reject/cancel may always fence it). A stale expected generation refreshes the card and grants nothing. Resolve approval and invalidate child state atomically before waking any Gate future.

Amendment CAS and approval CAS must use the same transaction/row boundary, comparing the displayed content generation and its server-bound proposal digest. If amendment wins, an approval frame for the previously displayed generation/digest is invalid even though the card ID is unchanged; the user must see and approve the updated generation. If approval wins, amendment fails because the approval is no longer pending. A generic runtime approval endpoint that lacks these expected-version fields must reject this card purpose rather than approving whichever digest happens to be current. Never carry a prior approved grant across amendment; an approved card cannot be amended in place.

Approved continuation must use the persisted final instruction/digest, await normal scheduling of the owner, and recheck target availability and run/source lifecycle at the exact adapter described above. A `card_dispatch` grant is exact and single-use, and cannot cover platform effects or arbitrary tools. Implement that adapter in this bounded release unit; do not defer it and claim working cards. Never resume legacy `commit_handoff_step` solely because an in-memory future says approved. No unrelated effect migration or broad Harness rewrite is included.

Capture source/course authorization revision from backend context when creating a card, not by parsing source names out of its text. The conservative initial policy invalidates the card on any change to its captured group source links/course bindings or required source versions. Revalidate through existing `scope`/`require_source` seams; losing a shared source link denies even if another group retains the bytes. Source deletion cannot be undone by a pending card's cached text. If the producer cannot establish provenance for source-derived content, the card must not promise that dependency remains usable.

At restart, restore bound cards only by joining the approval/private state to its canonical owner and current group/source state. Conversation events are projections and may be behind; they do not mint authority. A commit-before-publish crash replays the committed generation. A publish retry cannot resurrect a terminal card. Keep expiry normalized by Task Runtime; do not import Gate's `9999-12-31` sentinel into the runtime's finite approval policy (default 600 seconds, maximum 86400).

Mark interrupted feedback children/queued continuations as interrupted/cancelled and require a fresh explicit request; never auto-send on startup or client reconnect. In particular, filter `card_feedback` out of `_resume_safe_executor_continuations_after_startup`. Keep existing uncertain high-risk continuations blocked. `reapprove_recovered_continuation` currently has a route-message-specific contract; do not reuse it for cards without an exact dedicated adapter. A recovered bound pending card can support new feedback only if its owner still legitimately waits on that card. A missing worker continuation remains missing: approving it must not recreate prior high-risk work.

For old unowned cards, retain history and a clear “proposal needs renewal” projection, disable feedback/approval, and allow dismissal without executing the proposal. No SQL backfill based on timestamps, agent ID, event order, group name, last run, or renderer fields. Creating a fresh proposal from an explicit user request is a new governed lifecycle and must visibly supersede the old card.

## Bounded implementation sequence and remaining decisions

1. After the baseline gate, add the encrypted approval-state migration/contracts, verified key injection, encrypted card/continuation/projection serialization, and transactional repository/service methods for bind, admit, amend and settle. Null legacy state stays unbound. Add encryption, generation, request-key and lifecycle tests first.
2. Implement the single exact `GovernedProposeNextAdapter` in the real coordinator boundary through proposal, approval and dispatch, including scoped encrypted TaskEnvelope persistence/read and stable dispatch-intent/queue identity. Add Gate projection/recovery and the common runtime/legacy approval validator. Keep ownerless producers and every unrelated effect denied. This adapter is required in the same release unit, not postponed behind feedback completion.
3. Add card-kind continuation dispatch, scheduler admission, parent budget allocation, child-specific Gateway validation and cancellable aux flight; connect parent/group/source fences and restart exclusion.
