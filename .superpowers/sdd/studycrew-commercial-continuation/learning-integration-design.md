## Domain contract

Use typed Python contracts and matching strict Zod schemas, with explicit schema version, opaque IDs, integer record version and UTC audit timestamps. Reject extra fields, invalid dates/enums, NaN/Infinity, booleans masquerading as numbers, oversized strings/lists and foreign references. Every private object belongs to exactly one `group_id`; all referenced courses must be currently bound to that group. Course is the only installation-owned catalog object that may be explicitly bound into multiple groups; its shared fields are limited to course identity/name/term. Grade, mastery, plan, attempts and material selections are always group-scoped.

| Object | Minimum meaningful fields / invariants |
| --- | --- |
| Course | `course_id`, encrypted name/term, local/manual or mock origin, version, retired flag; group binding is an explicit existing GroupCourseBinding. Existing arbitrary legacy IDs migrate only within this verified-key store after resolution, not to guessed school courses |
| Assessment | `assessment_id`, group/course, label/kind, date-only or zoned timed deadline, optional duration, user-selected material evidence refs, version/status; missing date/time is unknown, never inferred school information |
| GradeSnapshot | `snapshot_id`, group/course, optional assessment, observed-at, grading scheme, optional finite score/max or explicit letter/pass-fail, provenance, acceptance state; immutable accepted observation with a new snapshot for correction. No absent grade => zero conversion; no cross-scheme averaging |
| StudyPlan | `plan_id`, group, bound course/assessment refs, input-evidence versions, availability/timezone, plan version, status `draft/active/superseded/archived`, approved task set; model proposal does not make an active plan |
| StudyTask | `study_task_id`, plan/group/course, user-visible label, effort minutes, optional material/concept refs, date/time slot, version, state `pending/completed/skipped`, optional `completed_at`, user-edited/locked fields; postpone is an event that changes the pending slot, not Agent pause |
| MasteryConcept | `concept_id`, group/course, approved concept label/evidence, revision, confirmed observations and algorithm version, bounded estimate or `unknown`; estimate is practice evidence, not a claim about the student's ability or predicted grade |
| PracticeAttempt | `attempt_id`, group/course/concept, question version/type, question/rubric evidence, student response, scoring provenance, bounded hint level, start/submitted times, `unscored/proposed/confirmed` result; response text is an authoritative record of what the user entered, model judgment is not |
| ReviewEvent | `review_event_id`, group/concept, scheduled local date, actual occurrence, linked attempt, explicit user rating/action, policy version and next due date; one occurrence key prevents repeated completion advancing review twice |

Internal supporting rows are operation requests, versioned proposals, evidence dependencies, learning event/outbox records and reminder delivery receipts. They are implementation metadata, not additional user-facing product objects. A proposal stores expected target versions and source/assessment/binding generations; stale proposal acceptance yields 409 plus the current safe view. User edits and complete/postpone/skip commands are authoritative after scope validation. A model cannot synthesize these commands by placing `approved`, `completed` or user identity in JSON.

Keep learning lifecycle distinct from Agent lifecycle:

| User/business action | Learning result | Agent/runtime consequence |
| --- | --- | --- |
| Ask for exam plan | Bounded draft proposal, then explicit accept/edit activates a plan | Scoped plan-generation run may succeed even while the draft awaits user decision |
| Complete StudyTask | Explicit completion event and version change | Does not fabricate an Agent run; completed Agent execution never automatically completes StudyTask |
| Postpone / skip | New date and pending state / skipped event; reminder replaced or cancelled | Does not map to pause/cancel of a currently generating Agent without an explicit linked cancellation decision |
| Request hint / quiz | One bounded coach response/proposal and attempt context | Ordinary governed run with cancellation/budget; run failure preserves prior confirmed learning state |
| Accept weakness / scoring proposal | Current-scope candidate becomes confirmed learning evidence | Separate from provider/tool permission approval; a content decision grants no model-egress authority |

## Storage, authorization and evidence

Create `backend/knowe_learning/repository.py` backed by `data_root/learning/learning.sqlite`, reusing `SQLiteDatabase`, `MasterKey` and `field_aad`. Inject the already verified local content key through one backend key-provider seam (today local knowledge loads `local_knowledge/master-key.dpapi`); do not independently generate a key for an existing encrypted learning DB or borrow the provider-credential lease as a storage key. Reuse the key-verifier pattern. Only learning readiness fails on unavailable/corrupt key, leaving unrelated offline functions available.

Encrypt names, grades, calendar/availability payloads, prompts/proposals, question/answer/rubric content, evidence provenance and user notes. Plain indexed columns can be opaque record IDs, keyed group/course/source selectors, version/state counters and event ordering. Avoid a durable plaintext timetable index: decrypt a bounded reminder/schedule snapshot in the backend and maintain the due heap in memory. If a future scale need requires plaintext due times, make that a documented privacy change rather than silently copying the source store's metadata tradeoff. Audit contains fixed action/result codes, opaque IDs and counts only. Never log arbitrary request bodies or model exceptions.

Commands use `(group_id, object_id, expected_version, request_key)`; request-key uniqueness also binds normalized command/payload digest so reusing a key with a different action is a conflict. Within one transaction check current entity state, group/course/source generation, expected version, apply event+state, replace reminder intent and append invalidation outbox. No lock is held across model/network/file-dialog I/O. Cross-store group/source changes use durable lifecycle intent and revalidation; an in-memory lock alone cannot make the JSON group store and SQLite learning DB atomic. Integrate with the existing deletion transaction rather than inventing a second incompatible coordinator.

Read/write APIs accept exactly one canonical group, not a renderer active tab or legacy project alias as authority. Backend resolves group existence/lifecycle/deletion fence and course binding; check again after long work and before committing. Archived groups are readable and do not accept plan/attempt/task mutations or deliver reminders; explicit restore can resume future pending reminders after reconciliation. A read-only dashboard can enumerate minimal projections across active groups because the one local student asked for that view; it cannot expose cross-group context to an Agent or serve as a search corpus.

Define an application `ApprovedLearningEvidence` resolver returning source ID, stable revision/content digest, chunk/locator, group/course binding identity, trust/approval status and sensitivity. Current RAG has chunk keyed content hashes but no complete source-generation learning acceptance contract; add the minimum immutable evidence snapshot/fingerprint plus dependency index. `EvidenceRef` shape validation alone is insufficient. An uploaded/indexed source is an untrusted document; an explicitly selected source version is approved for use as evidence, not an instruction to execute or proof that all extracted claims are true. Grade/concept/weakness extracted from it is a candidate until the user accepts the relevant fact. Deterministic plan timing may use the user's explicit exam/availability inputs immediately; LLM persistent proposals require accepted current evidence refs.

RAG search proposals must resolve to live, selected, same-group/course material and current content hashes at acceptance. Mem0 contributes only through a read interface that re-fetches current approved records, checks version/status/TTL/sensitivity and source scope. Since that integration is not present, the initial service uses no Mem0-based weakness personalization; it still supports manual inputs and verified practice evidence. A candidate, rejected, expired, stale or foreign memory can never influence persistent plan priority or mastery indirectly through a model summary. Store derivation refs for every inferred persistent value; unknown evidence IDs reject acceptance.

Cloud planning/coach requests go through the existing registry/gateway using a backend-created learning task tied to this group, selected evidence and finite budget. Capture immutable authority/provider binding for the operation and use request-bound credential resolution. Grade, weakness and student schedule association are sensitive even if regex DLP misses them; keep sensitive requests local or denied until exact-payload approval exists. Plan acceptance is not upload permission. No automatic cloud fallback from local OCR/embedding unavailability. No learning workflow invokes school writes, browser submission or graded-work impersonation; coach operates on practice and user-authorized explanatory material.

## Smallest end-to-end workflows

### Exam planning

Start with an offline deterministic baseline: user chooses group, actual bound courses/materials, assessment dates and available study windows; grades are optional. Validate positive effort minutes, finite horizon (initial cap 90 days/500 tasks), non-overlapping availability, course scope and actual evidence versions. Unknown effort/material coverage remains editable missing input. Do not invent an exam date, grade, syllabus or required hours.

Planner accepts a validated list of topics/tasks (manual or accepted generated outline). Stable scheduling order is earliest assessment deadline, then explicit user priority, then stable ID; place finite-duration sessions into free windows. Completed/skipped/locked tasks remain fixed. Do not double-book windows or exceed daily availability; expose unscheduled minutes/tasks with a reason. No hidden “catch up” overload. A user may manually change a recommendation; rescheduling preserves that override until the user chooses to unlock it. Algorithm/model/input versions accompany the draft and acceptance checks.

Assessment rescheduling first versions the Assessment and marks affected draft computations stale. Build a reviewable diff for remaining pending, unlocked tasks; keep completed history, IDs of unchanged tasks and manual locks. Earlier exams with insufficient time return an explicit remainder; later dates do not silently move user-fixed tasks. Accept the diff with expected plan/assessment versions, then atomically replace future reminder intents and increment export event sequences. An old model response cannot reactivate the previous exam date. Deleting/cancelling an assessment cancels its future generated tasks/reminders after a preview; do not delete independent user tasks without showing that scope.

Optional grades influence a draft only when their grading scheme and user-selected weighting are explicit and the snapshot is accepted. Default planning works without grades. Do not infer that a low score proves a particular weakness; generated weakness is a separate candidate with evidence review.

### Coach and review

An explicit practice session selects approved concepts/material and a practice goal. Diagnosis begins with what the user tried and bounded practice observations, then at most three graduated hints (concept cue, intermediate step, worked analogous example). Hint escalation is an explicit request, is recorded on the attempt, and does not imply lower mastery by itself. Treat instructions embedded in question/material text as data.

A quiz proposal contains a bounded question set (initially <=10), type, concept IDs, evidence refs and rubric/answer source. Do not accept generated authoritative answer keys solely because generation completed. For deterministic questions, validate against approved keys; for open answers, store model scoring as `proposed` and let the student confirm/correct. Persist submitted response before generating feedback so cancellation cannot lose it. Confirmed correctness plus actual hint use can update an operational practice estimate; model-inferred “you are weak at X” remains a review candidate. A user correction supersedes the scoring event, recomputes its affected aggregate and invalidates derived review suggestions.

Use a simple versioned, deterministic spacing policy first, e.g. user ratings `again/hard/good/easy` select the next interval from an explicit table with a bounded stage. Choose policy constants in implementation and freeze them in tests; do not claim educational efficacy from those constants. `ReviewEvent` records the rating and exact policy version. A skip/postpone changes the calendar, not mastery. Adaptive quiz selection may prioritize overdue concepts and confirmed unsuccessful attempts within the selected group/course; if evidence is missing, use stable coverage ordering and label insufficient data. No cross-group weakness pooling.

### Dashboard

Add backend `LearningTaskSummary` containing only group/task/plan IDs, task kind, pending/completed/skipped state, due local day/time, estimated minutes, safe user-approved display label and version. Default a task label to a neutral category if it would reveal grades, personal weakness, private question text or source excerpts. Keep detailed content in a group-scoped read. Today joins these summaries for presentation only; it never constructs one combined Agent prompt. Show clear separate labels for “学习任务” and “Agent 运行”. Clicking opens the owning group/task. Complete/postpone/skip from Today routes through the same scoped/versioned backend command, not a local optimistic-only flag.

## Dates, reminders and ICS

Store date-only deadlines as validated calendar dates, not midnight UTC. Timed appointments store local date+wall time+IANA zone and resolved UTC instant; retain the chosen offset/fold where needed. Default the local user's zone explicitly (Asia/Shanghai in the present environment), independent of OS locale strings. Use one injected clock in scheduling/reminder tests. Never parse a date-only string through JavaScript `new Date('YYYY-MM-DD')` for local-day meaning. Backend validates leap days and rejects malformed/timezone-naive timed values. DST nonexistent/ambiguous times need explicit disambiguation; no silent one-hour shift. Windows Python `zoneinfo` needs packaged zone data if unavailable; dependency/packaging choice is implementation work, not a download in this task.

Availability/review recurrence follows calendar days in the stored zone; elapsed durations/deadlines use UTC/monotonic time as appropriate. Date-only exams should remain date-only; the planner uses the end of the prior study day as its default scheduling cutoff unless the user supplies a time. On timezone change, preserve existing explicit assessment instants; preview reinterpreting floating study windows before applying. On resume or wall-clock jumps recompute due state from authoritative UTC and versions; never trust one long `setTimeout`.

Implement durable reminder intents in LearningRepository and a single bounded backend due scheduler that operates while the app/backend is running, including close-to-tray. It sends only a minimal notification lease/ID/version to a dedicated Electron-main learning notifier; main revalidates the authoritative due item before showing generic text. Add native `Notification` use with the existing app identity `io.studycrew.desktop`, permission/support handling and click navigation. Check trusted sender/frame on any renderer IPC; renderer cannot ask main to display arbitrary sensitive text or read arbitrary files. A click resolves the live group/task; deleted, unbound or expired targets open a safe unavailable state, never a stale cached question.

Reminder key `(study_task_id, due_version, reminder_offset)` prevents ordinary repeats; durable claim/ack with an expiry permits recovery. Exact-once delivery cannot be guaranteed across a crash between OS display and receipt write: choose at-most-one retry for an unacknowledged claim, generic text, and reconcile one consolidated overdue summary on restart rather than flood old notifications. Track `pending/claimed/attempted/acknowledged/cancelled/unsupported` distinctly; “display requested” is not proof the student saw it. Completion, skip, postpone, exam revision, archive, source invalidation and group deletion revoke old reminders before publishing the new state. Respect desktop notification preference; if disabled, retain in-app due status only. No background service, auto-launch or Windows Task Scheduler is assumed. Fully exited app cannot promise a native reminder; show that limitation and offer exported calendar use. If reminders while fully exited become a release requirement, that is a separate OS-scheduling integration gate, not an implicit install action.

ICS export is explicit local file creation, not school/calendar synchronization. Backend generates a bounded snapshot for user-selected plan/tasks with current scope/version and chosen detail level. Default summaries are generic; exclude grades, weakness, responses, provider IDs, source paths and private excerpts. Explain that the exported file is plaintext and may be imported into another calendar; give the user an actual preview of exported fields. Use `VCALENDAR/VEVENT`, stable opaque `UID`, UTC `DTSTAMP`, incrementing `SEQUENCE`, UTC timed `DTSTART/DTEND` or date-only `VALUE=DATE` with exclusive next-day end, UTF-8 CRLF and 75-octet folding without splitting Unicode code points. Escape backslash/comma/semicolon/newline and reject CRLF property injection; no ATTENDEE/ORGANIZER/school write or automatic remote URL. Keep app reminders and optional explicit calendar alarms separate to avoid accidental duplicate alarms.

`electron/learningIpc.ts` obtains canonical bytes through authenticated backend export by IDs/version, displays `showSaveDialog`, and writes only the user-chosen `.ics` destination with normal overwrite confirmation and atomic staging in that directory. No generic renderer `writeFile(path, bytes)` IPC. Revalidate the export token/generation after the dialog; source/group deletion or plan edit while the dialog is open invalidates it. Cancel writes nothing. Return a small result; do not log content/full path. Re-export reuses UID and changes sequence for edited events, but importers differ in update/cancellation handling. Previously exported/imported copies cannot be retracted by local deletion; never claim they were erased or updated remotely.

## Deletion and lifecycle semantics

Track reverse dependencies from plans/tasks/attempts/mastery/review proposals to sources, approved memory versions, assessments and group-course binding IDs. A status-only UI refresh is not deletion. All long-running plan/coach operations capture scope+input generations; changed generation prevents committing a late result.

- **Source unlink in one group:** immediately revoke that group's evidence availability, invalidate affected proposals and derived fields, remove material excerpts/question/answer payloads dependent on the removed source, cancel dependent future tasks/reminders or mark them `needs_material` in a separate validity field pending user replacement. Do not relabel them as completed/skipped. Preserve independent manual task completion only with neutral non-content metadata; the user sees which records lost evidence. Recompute mastery only from surviving confirmed observations. Other groups retaining a valid shared source link are unaffected.
- **Physical source deletion/last reference:** reconcile encrypted source store plus learning dependencies, candidates, hints/cache/context snapshots and native notification handles. Minimal opaque invalidation markers prevent a stale source result restoring content after restart. No retained excerpt disguised as event history. If the source is shared, preview distinguishes unlink versus removing all references; no silent destruction in other groups.
- **Course unbind:** revoke learning access and reminders under the specific binding generation; hide the private projection and mark its stored group/course data suspended for explicit rebind/review or scoped deletion. Rebinding a bare course ID does not revive old proposals/reminders automatically. Course deletion is a separate previewed operation cascading all chosen course-owned learning data; shared course catalog removal must enumerate other group bindings and cannot silently modify them.
- **Group archive/restore:** read-only historical learning view, reminders paused; restore reconciles deadlines/evidence and offers one overdue summary. **Group duplicate:** reuse explicit course/source bindings only under existing duplication behavior; do not copy grades, mastery, private attempts, consent or task completion implicitly.
- **Group deletion:** join the existing confirmed deletion intent: verify encryption access, freeze learning operations, cancel reminders, clean group-owned learning records/proposals/outbox payloads and renderer caches, preserve shared Course catalog/source rows referenced elsewhere, then acknowledge durable cleanup before the deletion receipt claims learning removal. Crash replay must remain idempotent. Neutral deletion receipts keep no task label/grade/question. Register learning store close/quiescence in the established SQLite teardown paths.
- **User correction/deletion:** CAS-versioned replacement supersedes old input/scoring/proposal generations and recomputes derived state. Stable evidence/input identity prevents a rejected weakness or corrected grade from reappearing when the same extraction batch is replayed with different wording. Text hashes do not prove arbitrary semantic equivalence. Do not retain deleted plaintext versions for audit; keep only minimal protected/opaque suppression metadata.

Database/WAL/backups may retain encrypted historical pages under existing storage policy; use established checkpoint/maintenance and backup behavior. This design promises no application-written plaintext learning content, not forensic erasure of OS memory or remote/exported calendar copies. UI teardown adds the learning store, review selection, due list and notification navigation cache to `groupTeardownCore`; deletion generation fences reject late HTTP/model/reminder responses before they repopulate them.

## Actual prerequisites, not new product questions

There is no design blocker requiring school docs or a real school API. Manual core, deterministic planning and mock import can be implemented offline after Unit P is accepted. Model-assisted personalization depends on a governed provider plus a reviewed current-evidence boundary; approved Mem0 reads remain unavailable until implemented and verified. Packaged Windows reminders/zone data and calendar interoperability need real release validation; reminders after full application exit require a separately specified OS lifecycle integration if desired. Learning cleanup must participate in group/source deletion before persistent derived data ships. These are concrete delivery gates, not grounds to expand into accounts, school credentials or multi-tenant architecture.
